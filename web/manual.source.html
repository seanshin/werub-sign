0.2 실서비스 개시 전 필수 (순서)

① 벤더/조달(리드타임 큼·먼저 착수)

  • 본인확인 사업자(PASS/명의) — KCB·NICE·드림시큐리티 등 본인확인기관. 계약→IDV_PROVIDER=pass+자격증명. 전자서명 법적효력의 전제(미계약 동안 identityDemo로 운영).
  • 알림톡/SMS 벤더 — NOTIFIER_PROVIDER=kakao|sms. 미계약 시 연동팀 직접 발송으로 운영 가능.
  • AWS KMS 계정/IAM(또는 온프레 PKCS#11 HSM) — CA 앵커 HSM 상주용.

② cutover(양팀 freeze 합의·1회성)

  1. P7 운영 DB clean-reset — 테스트데이터 제거·CA 재생성(3팀 freeze). 절차: clean-reset-runbook.md.
  2. KMS cutover — CA 앵커 KMS 상주 → assuranceLevel HSM_ANCHORED(P7과 함께 1회).
  3. 실 IDV/Notifier 전환 — 연동설정 콘솔에서 provider·자격증명 입력(런타임 즉시). 포털 identityDemo=false 확인.
  4. P8 시크릿 회전 — 팀 API키(rotate→팀 전환→commit) + webhook 시크릿(수신팀 dual-accept 후 flip) + 내부 키. 소비자별 격리.
  5. H2 관리자 콘솔 IP 제한(nginx) — Cloudflare 뒤 실IP 복원 또는 CF Zero Trust. CIDR 운영팀 확정.
  6. 하드닝·RBAC 확인 — 하드닝 라이브 활성(이미)·정규 관리자 계정 생성·임시비번 교체.

0.4 상태 확인 신호 (GET /v1/admin/ops-status)

  • config.keyCustody.hsm·서명/verify assuranceLevel = HSM_ANCHORED → KMS cutover 완료.
  • config.identity.provider = pass(mock 아님) → 실 본인확인(포털 identityDemo=false).
  • config.hardening.enabled=true → 하드닝 활성.

0.5 법적효력·인증 근거

구분내용
전자서명 법적효력전자동의의 효력 근거 = 전자서명법·민법. 환자 본인인증(PASS/명의→CI)이 필요한 이유 = 서명 당사자 동일성 확보. 그래서 실서비스 개시 전 본인확인 사업자 계약(V1)이 법적효력의 전제(현재 identityDemo는 시연/내부용).
EMR 인증제복지부·한국보건의료정보원 — 기능성·상호운용성·보안성 3영역. 보안성=12항목(F001~F012)(계정·권한·로그인실패·미사용차단·고유식별정보 암호화·마스킹·비밀번호 일방향·접속기록·수정이력·전자서명(F010)·백업·외부보관). 여기서 인증·접근통제는 시스템 사용자(의료진/직원) 인증이지 환자 본인인증이 아님.
핵심 구분EMR 인증(시스템 품질 심사) ↔ 전자동의 법적효력(환자 본인확인) = 별개 트랙. EMR 인증 통과에 환자 본인인증은 필수 아님 / 전자동의 효력엔 필요.
암호모듈(KCMVP)민간 의료법인 재단 → KCMVP 검증필 비강제. 표준 알고리즘(SHA-256+RSA-3072/ECDSA-P256)으로 EMR 보안성 충족. 공공 확장 시 CryptoProvider 추상화로 대비.
항목 문구·항목 수(12 일반/13 의원급)는 종별·인증기준 버전에 따라 가변 — 심사 제출 시 공식 PDF로 최종 확인. 대조표: docs/06-ops/emr-security-mapping.md, 증거가이드: emr-audit-evidence-guide.md.

0.6 보안·감사 핵심

  • 위변조방지 4중 방어: ①인증서(X.509 체인) ②서명(CMS/PAdES-LTA) ③감사 해시체인 ④TSA 시점앵커. 내부자 전체 재계산도 TSA 봉인 head 불일치로 탐지. (tamper-evidence-design.md)
  • 접근통제: 관리자=RBAC 세션(admin/operator/viewer) · 의료진=HIS SSO(JWKS·aud=sign) · 기계=소비자별 api-key(scope) · 환자/외부=1회용 포털토큰. 모든 행위 actor 귀속 감사(user:/staff:/소비자명). 콘솔 세션은 서버측 강제 비활동 자동 로그아웃(기본 15분, SESSION_IDLE_TIMEOUT_MIN — EMR 보안성 F004 미사용 접속차단)·동시 세션 수 제한(SESSION_MAX_CONCURRENT 기본 3 — ISMS-P 2.6.3)·로그아웃/비밀번호 변경 시 즉시 폐기.
  • 키 수탁(HSM 최소화): CA 앵커 2키만 HSM(go-live), 말단·TSA는 SOFT → 서명·타임스탬프 건당 HSM 비용 0. 개인키는 crypto-proxy로 앱 분리(운영).
  • 하드닝: PII GET 키강제·rate-limit(실IP)·callbackUrl SSRF 차단·보안헤더. 현재 라이브 활성(H2 admin IP만 잔여).
  • 감사 무결성 검증: GET /v1/requests/:id/audit/verify → 체인+TSA 앵커 valid. 접근로그 구조적 JSON(actor·reqId·IP, 비밀 미기록).

1. 개요·아키텍처

sign은 의료기관용 전자동의서·전자서명 트러스트 서비스다. 자체 PKI(2단 CA)·실 전자서명(RSA-3072/SHA-256·CMS/PAdES-LTA)·RFC3161 타임스탬프·감사 해시체인으로 전자동의의 법적 무결성·부인방지를 보장한다. HIS(병원정보시스템)·PACS가 API/Webhook로 연동한다.

구성 요소

구성역할
sign-core백엔드 API — 인증서 발급·서명·검증·폐기·감사·연동(NestJS)
sign-web관리자 콘솔 + 환자 포털 SPA(Next.js)
sign-postgres영속 저장소(PostgreSQL)

배포 토폴로지

공개 도메인 sign.example.org → Cloudflare(TLS) → nginx(443) → sign-web(SPA)·sign-core(API, same-origin /v1). HIS/PACS는 내부망 http://127.0.0.1:4100/v1(서버↔서버)로 호출. 서명 원본·키·민감정보는 원내망 고정(원내 구축형).

트러스트 모델: sign이 유일한 CA·발급·검증·폐기 주체. HIS/PACS는 발급을 sign에 위임하고 결과(serial)를 읽기전용 미러한다.

2. 콘솔 시작하기

관리자 콘솔: https://sign.example.org/admin. 로그인은 관리자 계정(아이디·비밀번호) 기반이다(C-4 다중관리자 RBAC). 로그인 성공 시 세션 토큰(만료 내장, 기본 8h)이 발급되며, 이후 모든 호출은 이 토큰으로 인증된다. 일정 시간(기본 15분, 내 계정에서 정책 상한 이내로 더 짧게 조정 가능) 화면 조작이 없으면 자동 로그아웃되며, 만료 1분 전 경고 창에서 ‘계속 사용’으로 연장할 수 있다(EMR 보안성 F004 미사용 접속차단). 콘솔 전용 API 키(CONSOLE_API_KEY)는 break-glass(비상) 폴백으로만 유지(로그인 화면의 ‘고급: API 키’).

3. 인증서 등록·관리

3.1 발급(등록)

인증서 발급(enroll)은 sign이 키쌍을 생성·개인키를 수탁한다. 호출자(또는 콘솔)는 공개키를 보내지 않으며 개인키를 보유하지 않는다.

ownerType본인확인(method)유효기간비고
PATIENT(환자)PASS / MOBILE_NAME / INPERSON 필수365일비대면/대면 본인확인 강결합
STAFF(의료진)STAFF_SSO + 면허번호365일HIS SSO 신뢰
WITNESS(외부 입회인)대면(INPERSON)1일단기 임시
PROXY(대리/보호자)대리인 본인 PASS/명의365일관계·대상(환자) 봉인

콘솔: 인증서 발급 메뉴 → ownerType·주체정보(subjectDn)·본인확인·면허 입력 → 발급. 결과로 serialNumber·X.509 PEM·assuranceLevel 발급. 모든 발급은 CERT_ISSUED 감사(해시체인) 기록.

멱등 아님: 발급은 매번 새 인증서. 발급받은 serial을 보관해 재사용하라(의료진은 SSO 토큰 sign_cert_serial 클레임으로 재사용).

3.2 신규 입사자(의료진) 온보딩 발급

의료진 인증서는 직원이 포털에서 직접 신청하지 않는다. HIS(EMR)가 온보딩 시점에 sign enroll API를 서버↔서버로 1회 대행 호출하고, 직원 계정에 serial을 저장(user.signCertSerial) → 이후 SSO 토큰의 serial로 재사용한다.

[온보딩 1회]  HIS → POST /v1/certificates/enroll
              (ownerType=STAFF, subjectDn, licenseNumber, identity.method=STAFF_SSO)
            → sign: X.509 발급 → serial 반환 → HIS가 user에 매핑
[이후]       의료진은 포털/SSO로 *서명만* (인증서 신청 단계 없음)

운영자가 콘솔 인증서 발급에서 수동 발급도 가능(예: 예외 처리). 발급 시점은 온보딩 자동 또는 첫 서명 시 lazy(ensureStaffCert) 모두 가능.

수신처 오기입 복구: 외부 서명자 이메일을 잘못 넣었더라도 아직 서명하지 않은 서명자라면 철회·재발행 없이 수신처만 고칠 수 있습니다(연동 시스템 경유). 정정하는 순간 기존에 보낸 링크는 즉시 무효화되므로(잘못된 수신자 차단), 정정 후 [발송] 또는 [독촉]으로 새 링크를 보내면 됩니다. 이미 서명한 사람은 다시 서명하지 않아도 됩니다.
다운로드 파일명: 완료 문서·감사추적인증서 파일명은 제목_구분_날짜_식별자.pdf 형식입니다(예: 정규직 근로계약서_체결본_20260728_68db9227.pdf). 여러 계약 파일을 한 폴더에 받아도 구분·정렬됩니다.
교부 링크 셀프 서비스: 수신자는 교부 화면에서 기한을 1회 연장할 수 있고(만료 전에만 가능 — 만료 후에는 발송자가 [교부 링크 재발급]), 담당자·보관용 주소로 문서를 전달할 수 있습니다(링크당 3회). 전달은 파일 첨부가 아니라 새 다운로드 링크 발송이며, 연장·전달 사실과 받는 주소(마스킹)는 계약 이력에 봉인됩니다.
교부 파일이 2개인 이유: 체결 완료 시 완료 문서(서명이 반영된 계약서 본문 — 각 장 QR 로 진위 확인)와 감사추적인증서(문서 해시·서명자·인증서·서명 이력 해시체인을 담은 증거 문서)를 함께 교부합니다. 감사추적인증서는 파일 자체가 전자서명(PAdES)으로 봉인되어 있어, 두 PDF 를 하나로 합치면 그 서명이 깨집니다 — 각각 보관하도록 안내하세요. 계약서만 제3자에 제출해야 하는 경우에도 완료 문서만 전달하면 됩니다(QR 로 진위 확인 가능).
개인정보 보호(공개 검증·프리셋): 완료 문서 QR의 공개 검증 페이지는 진위 확인 정보(서명 검증·해시·서명자)를 누구나 볼 수 있지만, 서명자가 직접 기재한 정보(계좌번호·주소 등)가 포함된 계약은 문서 자체를 공개하지 않습니다 — 사본이 필요하면 만료형 교부 링크를 사용합니다. 새 계약 프리셋 목록의 상대방 이메일도 마스킹되며, 프리셋을 실제로 적용할 때만 원문이 채워집니다.
첨부 보존: 계약 첨부는 기본적으로 영구 보관(계약 원본과 동일)입니다. 기관 보존연한이 정해져 있으면 CONTRACT_ATTACH_RETAIN_DAYS 를 설정해 종결된 계약(체결·만료·철회)의 첨부만 자동 파기할 수 있으며, 파기 사실은 계약 이력에 봉인됩니다(진행 중 계약은 대상이 아닙니다).
이력·무결성: 상세의 이력 탭에 생성·발송·독촉·접근암호 성공/실패·서명·교부가 해시체인으로 봉인되며(체결 시 TSA 앵커), 검증 탭에서 서명 전체 검증(overall)을 확인한다.
이메일 발송 채널: 원내 SMTP(SMTP_URL/SMTP_FROM 또는 연동 설정) 구성 전에는 provider=mock으로 실제 메일이 발송되지 않는다(알림·리마인더 화면에서 채널 상태 확인). 운영자 역할(operator)은 전자계약·내 계정·운영 매뉴얼 메뉴만 사용한다.

5. 연동 설정 (/admin/integrations)

외부 벤더 연동을 콘솔에서 입력하는 런타임 설정. 자격증명은 AES-256-GCM으로 암호화 저장되며 화면에 평문으로 다시 표시되지 않는다(설정 여부만 표시).

프록시 형태: provider를 실 벤더로 바꾸고 자격증명을 입력하면 무재배포로 연동이 "무장"된다. 단 실제 벤더 호출(verify()/send())은 사업자 계약·API 규격 확보 후 구현한다(현재는 스텁).

6. 보안·로그·감사

의료/IT 전자서명의 보안은 다층 방어(defense-in-depth) — 인증·인가, 암호화, 키 경계, 하드닝, 감사·위변조방지가 중첩된다. 아래는 각 도메인별 통제.

6.2 암호화·데이터 보호

  • 서명 알고리즘: SHA-256 + RSA-3072 / ECDSA-P256(표준). CMS(CAdES-BES) + PAdES-LTA(LTV).
  • 키 보관: SOFT 키는 AES-256-GCM으로 봉인(FileVault, 마스터키). 연동 설정 시크릿도 SecretBox(AES-256-GCM) 봉인.
  • 민감정보 비저장: 환자 CI는 HMAC 해시(pepper)만 저장(평문 미보관). 연락처는 마스킹(끝 4자리). 접근로그에 바디·키 미기록.
  • 전송: 공개=TLS(Cloudflare 엣지+Let's Encrypt). 서버↔서버 내부·mTLS 권장(운영가이드 §2).

6.3 키 수탁·경계

  • 개인키 앱 분리: 운영 권장 토폴로지 — sign-core는 개인키·마스터키·HSM SDK 미보유, crypto-proxy(사설망)가 키 수탁(KEY_SIGNER_DRIVER=proxy).
  • HSM 최소화: CA 트러스트 앵커 2키(Root·Issuing)만 HSM(KMS/PKCS#11), 말단(서명)·TSA 키는 SOFT → 서명·타임스탬프 건당 HSM 비용 0, 트러스트는 HSM-앵커 CA 사슬로 전파.
  • 영속·회전: CA/TSA 키 재기동 영속(볼륨), Issuing 회전(이력 보존·verifyChain 현재+이력).
  • attestation: caKeyCustody·caKeyCustodyProvider·assuranceLevel(SOFTWARE/HSM_ANCHORED)을 발급·webhook에 동봉(법적 감사 정직성).

6.6 위변조 방지 4중 방어

인증서(누가) × 서명/해시(무엇) × 해시체인(순서) × TSA(언제). 내부자가 전체를 재계산해도 TSA-봉인된 체인 head 불일치로 탐지된다. 검증: GET /v1/requests/:id/audit/verify(valid·chainValid·anchored·anchorTsValid·anchorMatchesChain). 설계: docs/02-design/tamper-evidence-design.md.

6.7 시크릿 관리·회전

  • break-glass: CONSOLE_API_KEY(계정 장애), SIGN_ADMIN_API_KEY(ca:admin·users:admin) — 최소·분리·감사.
  • ⚠️ CRYPTO_MASTER_KEY 회전 시 봉인 설정·관리자 세션 무효 → 재입력·재로그인(P8 비대상·별도).

7. 운영

7.1 보안 하드닝

SECURITY_HARDENING=true(또는 production)에서 활성. 현재 라이브 활성.

  • H3 PII GET(/v1/requests/:id·/audit)에 x-api-key 강제. 공개: verify/ocsp/crl/portal.
  • H4 rate-limit(공개 실IP/분, 기본 120). 서버↔서버(HIS/PACS, XFF 부재)는 면제 — trust proxy로 nginx 실IP 해석.
  • M1 Webhook callbackUrl SSRF(https 강제·사설망/메타데이터 차단).
  • M2 보안 헤더(helmet, HSTS).
  • H2(관리자 콘솔 IP 제한)은 실서비스 시 nginx로 적용 — Cloudflare 뒤이므로 실IP 복원(CF-Connecting-IP) 또는 CF Zero Trust 필요.

7.2 키수탁·HSM

HSM 상주 키 = CA 트러스트 앵커 2개(Root·Issuing)만. 말단(서명)키·TSA키는 SOFT(AES-256-GCM 봉인) → 서명·타임스탬프 건당 HSM 비용 0. 트러스트는 HSM-앵커 CA 사슬로 전파된다.

키수탁
Root CA / Issuing CAHSM(클라우드 KMS/온프레 PKCS#11) — 2키
말단(환자·의료진) / TSASOFT(FileVault 영속)
현재 라이브는 SOFT(FileVault, assuranceLevel=SOFTWARE). AWS KMS 주입 후 cutover 1회로 CA 앵커가 KMS 상주 → HSM_ANCHORED 전환. 어댑터(KMS·PKCS#11)는 구현·검증 완료, 조달만 남음.

7.3 시크릿 회전

API 키(HIS·PACS·콘솔·CA admin)는 무중단 회전 가능: POST /v1/admin/consumers/:name/rotate(신규키 grace) → 소비자 전환 → commit(구키 폐기). 재기동 후에도 유지하려면 .env.prod도 갱신(2-step). Webhook 시크릿은 env 교체 + HIS의 dual-accept 윈도우와 조율. go-live 직전 P8 회전 권장.

  • 인앱 스케줄러: Webhook 재시도·만료 배치를 주기 자동 실행(SCHEDULER_ENABLED 기본 on, SCHEDULER_WEBHOOK_RETRY_MIN 기본 5분·SCHEDULER_EXPIRE_MIN 기본 60분, 기동 시 catch-up 1회). 외부 크론 사용 시 SCHEDULER_ENABLED=false. 멀티노드는 한 워커만 활성 권장. 상태는 ops-status scheduler.
  • Webhook 재시도(수동): POST /v1/maintenance/webhook-retry(스케줄러가 자동 호출). 요청별 /webhooks로 HIS reconcile.
  • 만료 배치: POST /v1/maintenance/expire(크론).
  • 백업(자동화): 라이브 호스트 cron 이 매일 03:40 DB 를 덤프→gpg 암호화→로컬 14세대·오프사이트 30세대 보관(scripts/backup-sign-db.sh). 키 FileVault(볼륨)도 정기 백업 대상 — CA/TSA 키는 재기동 영속(볼륨 보존 필수). 분기 1회 복구 리허설 절차와 재해 복구는 docs/06-ops/backup-restore-runbook.md. ⚠ 백업 암호문을 잃으면 백업 전체를 열 수 없다(비밀번호 관리자에 사본 필수).

7.5 관리자 계정·RBAC (C-4)

콘솔 관리자는 로컬 계정(아이디·비밀번호 scrypt 해시, SignStore 영속)으로 인증하며 역할(관리자/운영자/열람자)로 권한이 결정된다. 계정 관리는 콘솔 사용자 관리(/admin/users, 관리자 전용) 또는 API(/v1/admin/users, users:admin).

  • 최초 부트스트랩: 계정 0개일 때 SIGN_ADMIN_PASSWORD(+SIGN_ADMIN_USER, 기본 admin) 설정 시 최초 관리자 자동 생성. 미설정 시 sign-admin break-glass 키(SIGN_ADMIN_API_KEY, users:admin 보유)로 첫 계정 생성.
  • 세션: 로그인 → HMAC 서명 세션 토큰(무상태·만료 내장, SESSION_TTL_MIN 기본 480분(8h)). 비밀키는 SESSION_SECRET 또는 CRYPTO_MASTER_KEY 파생. 마스터키 회전 시 기존 세션 무효(재로그인).
  • 2차 인증(2FA/TOTP): 인증앱(Google/Naver Authenticator 등) 기반 로그인 강화. 내 계정 화면에서 등록(QR 스캔 또는 수동키 → 6자리 코드 확인 → 활성화·복구코드 8개 발급). 활성 계정은 로그인 시 1차(ID/PW) 후 인증앱 6자리 코드(또는 복구코드)를 추가 입력. 시크릿 AES-256-GCM 봉인·복구코드 1회용. 기계 키(HIS/PACS/ERP) 경로는 무관.
  • 비활동 자동 로그아웃(EMR 보안성 F004 · 서버측 강제): 콘솔에서 일정 시간 입력(마우스·키보드·스크롤·터치)이 없으면 자동 로그아웃. SESSION_IDLE_TIMEOUT_MIN(기본 15분, 절대 만료 SESSION_TTL_MIN 초과 시 TTL로 캡). 운영 모드(하드닝/production)에서는 0(비활성)을 허용하지 않고 15분으로 강제(F004 보장) — 비운영에서만 0으로 끌 수 있다. 서버측 세션 레지스트리가 매 요청 마지막 활동시각을 점검해 idle을 강제(클라이언트 JS 의존 아님) — 토큰을 보관·복제해도 서버가 차단. 만료 1분 전 경고 창에서 ‘계속 사용’으로 연장.
  • 동시 세션 수 제한(ISMS-P 2.6.3): 동일 사용자의 동시 세션을 SESSION_MAX_CONCURRENT(기본 3, 0=무제한)로 제한 — 초과 로그인 시 가장 오래된 세션을 축출. 즉시 폐기: 로그아웃·비밀번호 변경 시 서버 세션을 즉시 무효화(절대 만료 전이라도). 현재 값·활성 세션 수는 /v1/admin/ops-status config.session·콘솔 시스템 상태에서 확인(enforcement=server). 서버가 세션을 종료한 경우(축출·폐기·만료)에도 콘솔은 다음 동작 시 자동으로 로그인 화면으로 전환(전역 401 처리)된다.
  • 안전장치: 마지막 활성 admin 강등·비활성 차단(409). 계정 비활성화 시 기존 토큰 즉시 무효. 모든 변경은 감사(admin:users)·로그인은 admin:auth에 봉인.
  • break-glass: CONSOLE_API_KEY는 계정 인증 장애 시 폴백(로그인 화면 ‘고급: API 키’). 단 users:admin 미보유 → 사용자 관리는 불가(최소권한).

7.6 2단계 인증(2FA·TOTP) 운영

인증앱 기반 2단계 인증으로 관리자 로그인을 강화한다(ISMS-P 2.5.3 인증·개인정보 안전성 확보조치의 ‘안전한 인증수단’ 강화). 1차 비밀번호 + 2차 인증앱 일회용 코드(TOTP, RFC6238). 사용자별 자율 등록(현재). 기계 키 연동(HIS/PACS/ERP)은 2FA 무관.

등록 절차(런북) — 콘솔 내 계정 → 2단계 인증 설정:
  1. 인증앱(Microsoft / Google / Naver Authenticator, Authy, 2FAS 등)에서 QR 스캔(또는 화면의 수동 키를 직접 입력).
  2. 인증앱에 표시되는 6자리 코드를 입력해 활성화.
  3. 발급되는 복구코드 8개를 안전한 곳(비밀번호 관리자·금고)에 보관. 각 1회용이며 기기 분실 시 로그인에 사용.
  • 로그인 흐름: 2FA 활성 계정은 1차(아이디/비밀번호) 통과 후 세션이 바로 발급되지 않고 인증코드 입력 단계로 전환된다. 인증앱 6자리(또는 복구코드) 입력 → 검증 성공 시 세션 발급. 1차만으로는 어떤 작업도 불가(단기 챌린지 토큰 5분).
  • 기기 분실·교체: ① 보관한 복구코드로 로그인 → 내 계정에서 2단계 인증 해제 후 재등록(새 기기). ② 복구코드도 없으면 다른 관리자(admin)가 해당 계정을 비활성화→재생성하거나, break-glass(CONSOLE_API_KEY/SIGN_ADMIN_API_KEY)로 복구. (관리자가 타 계정 2FA를 직접 리셋하는 기능은 후속 예정)
  • 해제: 내 계정에서 현재 인증코드(또는 복구코드) 확인 후 해제. 해제 시 복구코드도 폐기된다. 재등록하면 시크릿·복구코드 모두 새로 발급(기존 인증앱 항목은 수동 삭제).
  • 인증앱 표기·로고: 발급자(issuer)는 “WeRUB.B Sign”으로 표시. 로고는 image= 파라미터(/mfa-logo.png)를 지원하는 앱(Authy·2FAS 등)에서만 보이며, MS·Google Authenticator는 로고 미표시(이름만). 등록 화면 QR 중앙에는 브랜드 로고가 항상 삽입된다. 로고 교체는 web/public/mfa-logo.png(또는 MFA_LOGO_URL).
  • 보안: 시크릿은 AES-256-GCM 봉인(CRYPTO_MASTER_KEY) 저장, 복구코드는 sha256 해시(1회용 소모). 챌린지 토큰 5분 만료. 모든 행위 감사(MFA_ENABLED/VERIFIED/FAILED/DISABLED, admin:auth).
  • 코드 불일치 시: 인증앱은 휴대폰 시계 기준 코드를 생성하므로 기기 시간 자동설정(NTP)을 확인(±30초 허용). 그래도 안 되면 복구코드로 로그인 후 재등록.

8. HIS·PACS 연동

HIS/PACS는 EXTERNAL 모드로 연동(현재 라이브). 발급·서명·검증은 sign이, 트리거·기록(미러)은 HIS/PACS가 담당.

  • 인증: 기계 API 키(x-api-key, scope), 의료진은 HIS SSO(JWKS, iss=hospitalrun·aud=sign) 검증.
  • 발급 위임: HIS는 인증서를 발급하지 않고 sign enroll 호출. 결과 serial 미러(읽기전용).
  • Webhook: 서명 완료/철회/만료/개정(request.superseded, supersededBy 포함) 시 HIS로 HMAC 서명 통지(eventId 멱등·재시도).
  • 완료 확인: Webhook 또는 공개 GET /v1/verify/:id 폴링.

상세 명세는 docs/05-handoff/ 문서 세트 참조(HIS·PACS 통합 가이드·결정사항).

9. EMR 인증 대응

EMR 인증제(보안성)는 EMR 본체(HIS) 심사이며 sign은 F010 전자서명·F008 접속기록·F009 위변조방지·F005 고유식별정보 암호화·F004 미사용 접속차단(콘솔 비활동 자동 로그아웃)을 분담·증빙한다. HSM·환자 본인인증은 보안성 필수요건이 아니다(각각 부인방지 보강·전자동의 법적효력 트랙).

증빙: 대조표 docs/06-ops/emr-security-mapping.md, 증빙 가이드·시연 스크립트 npm run emr:demo, HIS 분담 체크리스트 docs/05-handoff/emr-security-his-checklist.md.

항목 코드·개수(12/13)는 의료기관 종별·인증기준 버전에 따라 다르다. 심사 제출 전 공식 세부 PDF로 최종 확인하라.

2FA 기기 분실보관한 복구코드(1회용)로 로그인 → 해제 후 새 기기 재등록. 복구코드도 없으면 다른 admin이 계정 비활성화→재생성 또는 break-glass 키로 복구.
인증앱에 로고가 안 보임MS·Google Authenticator는 커스텀 로고 미지원(이름 ‘WeRUB.B Sign’만 표시). 로고는 image= 지원 앱(Authy·2FAS 등)에서만. 등록 QR 중앙 로고는 항상 표시.
검증 탭이 ‘검증 실패’로 보임(미서명)서명 0건(아직 서명 전) 요청은 ‘서명 대기 중’으로 표시(정상). 1건 이상 서명된 후에만 성공/실패 판정.
대시보드가 자동 갱신 안 됨실시간(SSE) 미연결 시(프록시 버퍼링 등) 수동 새로고침으로 폴백. 일괄작업 선택 중에는 자동 갱신 보류(혼동 방지).
CSV 내보내기 401requests:write 스코프 필요(열람자 제외). 현재 필터(검색·상태·출처·기간)가 그대로 반영됨.

12. API 레퍼런스(요약)

OpenAPI: docs/openapi.json(운영 /api-docs는 기본 비노출). 목록 페이지네이션: requests·certificates·admin/notifications·audit-events는 ?limit=&offset= 지원(미지정 시 전체, limit max 200). 응답 { data:[…], page:{ total, limit, offset } }(data 배열 하위호환). 서버측 검색: GET /v1/requests·GET /v1/certificates는 ?q=(부분일치 — 요청 제목·문서ID·요청ID·참가자명 / 인증서 시리얼·주체·유형·면허) 지원. ?status=(정확일치)는 GET /v1/requests 한정(인증서 상태는 만료 계산 표시값이라 서버 필터 아님). page.total은 일치 결과 수. 기간 필터: GET /v1/requests는 ?days=(최근 N일) 또는 ?from=&to=(ISO 범위, 대시보드 시작~종료일 직접 지정)로 생성일(createdAt) 기준 필터 — 대시보드 기본 최근 90일로 working set 한정. 대시보드 추가 필터: ?createdBy=(출처 — HIS/PACS/ERP/콘솔)·?signMode=(APP/PORTAL/MULTI)·?incomplete=true(미완료=CREATED·IN_PROGRESS)로 좁히기. 출처·서명모드는 인덱스 컬럼(createdBy·signMode)으로 DB 푸시다운. 확장성: 서명요청·인증서 목록은 검색·필터·정렬·페이지·카운트를 DB 레벨로 푸시다운 → 전체 메모리 로드 없이 페이지당 일정 비용. 서명요청=인덱스 컬럼 status·reqCreatedAt·searchText(상태·기간·최신순), 인증서=ownerType·notBefore·searchText(CA 제외·발급 최신순; 상태는 페이지에서 계산·유형 탭/초성은 콘솔 정제). CSV 내보내기(심사·보존): 대시보드·인증서 목록·발송 이력에 내보내기 버튼 — GET /v1/requests/export.csv(현재 검색·상태·기간 필터 반영)·/v1/certificates/export.csv·/v1/admin/notifications/export.csv. 감사 스트림도 /v1/audit-events/export.csv·/v1/admin/audit/export.csv(?q=&eventType=&from=&to= 검색 일치 전부, 페이지 무관). UTF-8 BOM(한글 Excel)·attachment. 연락처는 마스킹값만·CI 미포함(평문 미노출). 주요 엔드포인트:

부록 B. 운영 절차 (단계별 런북)

실제 운영자가 따라 하는 단계별 절차. 각 절차는 콘솔 메뉴 또는 API로 수행한다.

B.1 API 키 무중단 회전 (P8)

HIS·PACS·콘솔·CA admin 키를 다운타임 없이 교체. 콘솔 API 키 회전(CA Admin 키 필요).

  1. rotate: 대상 소비자(예: hospitalrun) '키 회전' → '자동생성' 선택 → 새 키가 1회 표시되면 복사(다시 못 봄). 이 시점부터 구키·신키 둘 다 유효(grace, activeKeys=2).
  2. 소비자 갱신: 새 키를 해당 시스템(HIS/PACS)의 sign 연동 설정에 반영·재기동. 호출이 새 키로 전환됐는지 확인.
  3. commit: '회전 계속(commit)' → 유지할 키(새 키) 입력 → 구키 폐기(activeKeys=1). 이후 구키는 401.
  4. 영구화: 재기동 후에도 유지되도록 서버 .env.prod의 해당 키 값도 새 키로 갱신(회전은 in-memory).
실패 시: commit 전이면 구키가 계속 유효하므로 롤백 부담 없음. 새 키 분실 시 구키 유지 상태에서 다시 rotate.

B.2 신규 의료진 인증서 발급 (온보딩)

  1. HIS가 온보딩 시 POST /v1/certificates/enroll(ownerType=STAFF, subjectDn, licenseNumber, identity.method=STAFF_SSO) 1회 호출(부록 A.1).
  2. 반환된 serialNumber를 직원 계정(user.signCertSerial)에 저장.
  3. 이후 의료진 서명은 SSO 토큰의 sign_cert_serial 클레임으로 해당 인증서 재사용 — 추가 발급 없음.
  4. 예외/수동 발급은 콘솔 인증서 발급에서 가능.

B.3 Webhook 장애 대응 (HIS 수신 실패)

  1. 증상 확인: 콘솔 시스템 상태 → Webhook 적체(FAILED/DEAD) 또는 요청 상세 Webhook 탭.
  2. 인앱 스케줄러가 자동 재시도(기본 5분, 최대 8회 후 DEAD). HIS 복구 후 다음 주기에 자동 전송.
  3. 즉시 재시도: 요청 상세 Webhook 탭의 '재시도' 또는 POST /v1/maintenance/webhook-retry.
  4. DEAD(8회 초과) 건은 HIS가 GET /v1/requests/:id/webhooks 또는 공개 GET /v1/verify/:id로 reconcile.

B.4 인증서 폐기·중단

  1. 콘솔 인증서 목록·관리에서 대상 검색.
  2. 중단(suspend): 일시 정지(가역) — 향후 서명만 차단, 재개 가능. 폐기(revoke): 영구.
  3. 과거 서명은 서명 시점에 유효했으면 그대로 유효(LTV) — 폐기가 소급 무효화하지 않음.
  4. 폐기 상태는 GET /v1/ocsp/:serial·/v1/crl로 검증. 모든 폐기/중단은 행위자(actor) 감사 봉인.

B.5 벤더 연동 활성화 (PASS·알림톡 계약 후)

  1. 사업자 계약·API 규격 확보 후 sign 측 verify()/send() 실 REST 구현·배포(스텁→실구현).
  2. 콘솔 연동 설정에서 provider(pass/kakao 등)·endpoint·apiKey 입력 → 저장(암호화). 즉시 런타임 반영.
  3. 테스트 1건으로 본인확인/발송 동작 확인. 문제 시 provider=mock으로 즉시 롤백.
  4. HSM/KMS는 캡처 설정 후 cutover(재배포) 필요 — assuranceLevel SOFTWARE→HSM_ANCHORED 전환.

부록 D. 자주 묻는 질문 (FAQ)

Q. 의료진은 서명할 때마다 인증서를 발급받나?

아니다. 온보딩 시 1회 발급 후 SSO 토큰의 serial로 재사용한다(부록 B.2).

Q. 인증서를 폐기하면 과거 서명도 무효가 되나?

아니다. 서명 시점(TSA)에 유효했으면 그 서명은 LTV로 유효 유지된다. 폐기는 향후 서명만 차단.

Q. 환자 본인인증(PASS)이 아직 mock인데 EMR 인증에 문제 없나?

EMR 보안성은 의료진(시스템 사용자) 인증 기준이라 환자 본인인증은 필수요건이 아니다. 환자 본인인증은 전자동의 법적효력 트랙(부록 C·§9).

Q. 연동 설정에 입력한 API 키는 안전한가?

AES-256-GCM으로 봉인 저장되며 화면·API로 평문 반환되지 않는다(설정 여부만 표시). 변경은 settings:write 권한만 가능.

Q. HIS가 다운되면 완료 알림(Webhook)은 어떻게 되나?

FAILED로 표시되고 인앱 스케줄러가 자동 재시도(최대 8회). HIS 복구 후 자동 전송되며, 폴링(verify)으로도 reconcile 가능(부록 B.3).

Q. 목록이 너무 많으면?

목록은 서버 페이지네이션(?limit=&offset=) 지원. 콘솔은 페이지 컨트롤로 탐색.

Q. 키를 클라우드 HSM으로 올리면 비용이 많이 드나?

HSM 상주 키는 CA 앵커 2개뿐(말단·TSA는 SOFT)이라 서명 건당 HSM 비용 0, 키 보관료만 고정(§7.2).

Q. 관리자 콘솔은 누구나 접근하나?

로그인(콘솔 API 키) 필요. 운영 매뉴얼도 인증 뒤에서만 접근. 고권한 작업(CA·키 회전)은 별도 Admin 키(ca:admin).
