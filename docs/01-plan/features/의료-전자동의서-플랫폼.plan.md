# 의료-전자동의서-플랫폼 (sign) Planning Document

> **Summary**: 기존 자체개발 HIS(Hospital RUN)에서 분리된 **독립 전자서명 트러스트 서비스**. 자체 PKI(2단 CA)+RFC3161 TSA+PAdES-LTA 기반 법적 무결성을 제공하고, **개인인증된 환자포털 앱(원내/원외 통합)·의료진 포털·대면 fallback** 다채널 서명을 Hospital RUN과 API/Webhook/SSO로 연동한다. 민간 의료법인(KCMVP 비강제).

## 1. Overview

### 1.1 Purpose

자체개발 HIS인 **Hospital RUN**에는 이미 동의서/서명 인프라(ConsentForm, 템플릿, 태블릿/포털 서명)가 구축되어 있으나, 서명의 **법적 무결성이 mock 수준**(실제 PKI/TSA/HSM 없음)이다. 본 프로젝트는 **법적 효력을 갖춘 독립 전자서명 서비스(sign)** 를 구축해 Hospital RUN 및 향후 타 시스템에 API로 제공한다.

### 1.2 Background (AS-IS 코드 분석 결과)

**Q1 — HIS 정체**: Hospital RUN = 자체개발 HIS (Next.js 15 + NestJS + Prisma/PostgreSQL 16, 314 DB모델, FHIR R4). 상용 패키지 아님 → DB/API 직접 연동 자유도 높음.

**Q2 — EMR 인증**: 인증 **예정** → 기능성·상호운용성·보안성 3영역 설계 단계 반영 필수.

**Q3 — 동의서 현황 (이미 구축됨)**:
- `ConsentForm` (다자서명: 환자/보호자/의사/입회인/간호사, signMode TABLET/PC/PORTAL/PAPER, consentType SURGERY/ANESTHESIA/…)
- `ConsentTemplate` (버전관리), `ConsentSignSession`(1회용 토큰), `ConsentSigningDevice`(태블릿 페어링·SSE)
- 환자포털 `/portal/consents`, 공개 서명 `consent-sign/:token`
- 모듈: `consent`, `consent-template`, `document-sign`, `blockchain-cert`, `blockchain-anchor`, `audit`/`audit-enhanced`(BTG·이상탐지), `hie`

**핵심 격차 (가장 중요)**: 기존 `blockchain-cert`/`document-sign`은 **mock PKI**.
- 인증서 발급: 실제 키쌍/CA 없이 외부에서 받은 `publicKey`로 만료 2099 무기한·즉시 ACTIVE 발급
- 서명 검증: `crypto.verify`(공개키 검증)가 아니라 `sha256(signatureValue)` 단순 해시
- TSA(신뢰 시점), HSM(키 보호) 없음 → **전자서명법 신뢰요건·EMR 보안성 미충족**

## 2. Scope

### 2.1 In Scope

- [ ] **독립 서명 서비스(sign)** — 자체 DB(인증서·키·서명·타임스탬프·감사로그), API/Webhook/SSO
- [ ] **실 PKI**: 자체 **2단 CA**(오프라인 Root + 온라인 Issuing), 실제 키쌍, `crypto.sign/verify`, 인증서 수명·**폐기 검증(CRL/OCSP 응답자)**
- [ ] **서명 포맷**: **PAdES-B-LTA** + LTV(인증서 만료 후 장기검증) — 동의서 보존기간 대응
- [ ] **TSA**: RFC3161 타임스탬프(자체→외부 공인 교체 추상화)
- [ ] **키 보호**: 키스토어 추상화 (**SOFT 암호화 보관 시작 → 원내 물리 HSM 별도 도입**, 무중단 교체)
- [ ] **감사추적**: 감사추적인증서 + AuditTrail 해시체인 + TSA 앵커링(위변조 탐지)
- [ ] **문서 무결성**: 문서 해시 봉인, 위변조 검증 API (원본 해시 대조)
- [ ] **인증서 발급(enroll)**: 환자(휴대폰 본인인증 PASS/명의+CI) / STAFF(HIS 면허확인) / 외부입회(임시·제한)
- [ ] **통합 채널**: 개인인증된 **환자포털 앱(원내/원외 동일)** primary + **의료진 포털**(STAFF) + 대면 태블릿 fallback
- [ ] **다채널 단일 봉투**: 환자(앱)·의료진(포털) 순차 서명을 동일 SignatureRequest로 묶음
- [ ] **발송(fallback)**: 카카오 알림톡/SMS + 서명 웹뷰 (DMZ, 앱 미설치자용)
- [ ] **Hospital RUN 연동**: 서명요청/검증 API + 완료 Webhook + **STAFF SSO 신뢰경계(JWKS)** → [관계 정의](../../02-design/integration-hospitalrun.md)
- [ ] **mock 전면 재구축(clean replacement)**: 기존 `blockchain-cert`/`document-sign`/`SignedDocument` 제거 (개발중, **마이그레이션 없음**)

### 2.2 Out of Scope

- 동의서 임상 콘텐츠·템플릿·업무흐름 UI → **Hospital RUN 유지** (sign은 서명/무결성만 담당)
- 원내 다자 서명 UX 신규 개발 → **이미 구축됨**, 연동만 (필요 시 미세 개선)
- 전자계약(B2B 일반 계약), 결제/정산
- 퍼블릭 클라우드 SaaS 제공 (원내 구축형 유지)

### 2.3 책임 경계 (sign ↔ Hospital RUN)

> 관계 유형 = **Provider(sign)·Consumer(Hospital RUN)**, 독립 배포·독립 DB, 계약(REST/Webhook/SSO)으로만 결합. 상세: [integration-hospitalrun.md](../../02-design/integration-hospitalrun.md)

| 책임 | sign (Provider) | Hospital RUN (Consumer) |
|---|---|---|
| 임상 콘텐츠·템플릿 | — | ✅ ConsentForm/Template |
| 서명 채널·UI | 서명 웹뷰(무결성) | ✅ 환자앱·의료진포털·워크스테이션·태블릿 |
| PKI 키·인증서(환자/STAFF/외부입회) | ✅ CA·키쌍·HSM | — |
| 서명/검증/TSA | ✅ | — (호출만) |
| 감사추적(서명 무결성) | ✅ 해시체인·앵커링 | 임상 감사는 자체(audit-enhanced) |
| 본인인증 | ✅ PASS/명의/STAFF SSO 검증 | 인증수단 제공(앱/SSO) |
| 계정·임상데이터 | 참조만(externalRef) | ✅ Patient/User/Encounter |
| 데이터 소유 정본 | 서명/인증서/타임스탬프/서명원본 해시 | 동의서 본문·환자정보 |

## 4. Success Criteria

### 4.1 Definition of Done

- [ ] 자체 PKI(2단 CA·실 키쌍/서명/검증) + RFC3161 TSA + PAdES-LTA 동작
- [ ] 인증서 발급(enroll: 환자 PASS/명의+CI, STAFF 면허) + CRL/OCSP 폐기검증
- [ ] 기존 mock `document-sign`/`blockchain-cert` 제거(clean replacement)
- [ ] Hospital RUN 연동(서명요청 API + 완료 Webhook + STAFF SSO JWKS) E2E
- [ ] **환자앱 채널 E2E**(등록→본인인증→서명→TSA→Webhook) + **의료진 포털 서명** E2E
- [ ] 다채널 단일봉투(환자앱+의사포털 순차) E2E + 대면 fallback
- [ ] LTV: 인증서 만료 후 검증 성공
- [ ] EMR 인증 3영역 자가점검 통과
- [ ] 보안(망분리/키/민감정보)·법무(효력) 검토 완료

### 4.2 Quality Criteria

- [ ] 위변조 검증 100% 검출, 서명검증 위양성 0
- [ ] 핵심 경로 테스트 커버리지 80%+
- [ ] 침투테스트 Critical 0건, 감사로그 누락 0건

## 5. Risks and Mitigation

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| 자체 PKI 공신력 한계(공인 아님) 법적 다툼 | High | Medium | TSA·감사추적 강화, 공인/외부TSA로 교체 가능하게 추상화(단계적) |
| 기존 mock 서명 데이터/흐름과 충돌 | Low | Low | ✅ 해소 — 개발중이라 mock 전면 재구축(clean replacement), 운영 데이터·마이그레이션 없음 |
| 독립 서비스 분리로 연동 복잡·공수 증가 | Medium | High | 명확한 API 계약·Webhook 멱등성, Outbox 패턴 재사용 |
| 비대면 본인인증 신뢰성/계약(Q4) | High | Medium | PASS/명의+CI, 앱 step-up, 고위험 대면 fallback |
| **앱 도입률**(고령/미설치/외국인) | Medium | High | 대면 태블릿 fallback 상시 유지(앱 우선 하이브리드) |
| **두 DB 정합성**(Webhook 유실 시 ConsentForm↔SignatureRequest 불일치) | High | Medium | Outbox 재시도·eventId 멱등 + 주기 정합성 reconcile 배치 |
| STAFF SSO 신뢰경계 오류 | High | Low | JWKS 검증·발급자 고정·토큰 수명/acr 검증 |
| 서명키 유출 | High | Low | 키스토어 추상화·격리(SOFT 암호화→HSM), 접근통제·감사 |
| EMR 인증 보안성 미충족 | High | Medium | 인증기준 체크리스트 설계 반영, 사전 자가심사 |
| 서명 서비스 장애→대면 서명 중단 | High | Low | 이중화, Hospital RUN 내 폴백(임시 PAPER) |

## 6. Architecture Considerations

### 6.2 Key Architectural Decisions

| Decision | Selected | Rationale |
|----------|----------|-----------|
| 서비스 형태 | **독립 서명 서비스(standalone)** | 플랫폼화(목표④), 타 시스템 재사용, 관심사 분리 (사용자 결정) |
| 무결성 수준 | **자체 PKI + RFC3161 TSA (실용적)** | 비용↓·원내완결, 공인/외부TSA로 교체 가능 추상화 (사용자 결정) |
| 배포 | **원내 구축형 + DMZ** | 민감정보 원내 고정, 원외 비대면은 게이트웨이 |
| 연동 | **API + Webhook (멱등)** | EMR 상호운용성, 자동 반영 |
| 키 보호 | **키스토어 추상화** (SOFT 시작→원내 물리 HSM, AWS HSM 불요) | 인증 보안성, 무중단 교체 |
| 서명 포맷 | **PAdES-B-LTA + LTV** | 동의서 보존기간 장기검증 |
| 폐기 검증 | **CRL/OCSP 응답자** | 표준 폐기검증·외부 검증 |
| 채널 | **앱 통합(원내/원외)+의료진 포털+대면 fallback** | 강한 개인인증·채널 단순화 |
| 암호 컴플라이언스 | **표준 알고리즘(KCMVP 비강제, 민간)** | 의료법인 재단=민간 |
| 기존자산 | **consent UI/흐름 유지, 서명코어만 대체** | 중복개발 방지 |

### 6.3 목표 배포/연동 구조

```
[인터넷] 환자폰(알림톡/SMS)
   │ HTTPS (서명 웹뷰만)
[DMZ] sign-gateway : 본인인증 중계 · 발송 · 서명웨뷰 reverse-proxy
   │ 제한 포트
[원내망]
   ├─ Hospital RUN (HIS)  ──(서명요청 API)──▶  sign-core
   │     consent/template/UI            ◀──(완료 Webhook)──
   └─ sign-core 서비스
         ├─ PKI(CA·키쌍·crypto.sign/verify)
         ├─ TSA(RFC3161)   ├─ HSM/키스토어(추상화)
         ├─ 감사추적·검증센터   └─ 서명DB(인증서/서명/타임스탬프)
```

### 6.4 Clean Architecture (Enterprise)

```
sign/ (독립 NestJS 서비스 권장 — Hospital RUN과 동일 스택 재사용)
  presentation/   : 서명 웹뷰, 연동 API, Webhook 송신
  application/    : 서명요청/완료/검증/본인인증 유스케이스
  domain/         : Certificate · Signature · Timestamp · AuditTrail · Identity
  infrastructure/ : CA · TSA · HSM · 발송 · Hospital RUN 연동 · DB
```
