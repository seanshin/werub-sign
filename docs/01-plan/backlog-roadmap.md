## 트랙 D — 코드 감사 후속 (2026-07-28 감사) — **종결**

4개 서브에이전트 병렬 감사. **F1~F19 + R1~R8·R10~R15 + D1~D7** 을 v1.15.1 → v1.23.0 으로 수정·배포 완료(**정책 D1~D7 전건 종결**).


**마지막 2건도 v1.26.0 에서 종결** — 보류 사유였던 "전제 대기"를 기다리지 않고 우회했다:
| # | 내용 | 보류 사유를 어떻게 없앴나 |
|---|---|---|
| R9 | 첨부 blob 청크 스트리밍(전량 메모리 적재 해소) | 착수 조건이던 **기존 blob 마이그레이션을 제거** — v1(단일 슬롯)·v2(청크 매니페스트) **dual-read** 로 기존 데이터를 그대로 두고 신규 업로드만 청크 저장. 읽기는 청크별 SHA-256 을 **방출 전** 검증 → 피크 힙이 파일 크기 대신 청크(256KB)로 고정 |
| R16 | 인프로세스 잠금 → **저장소 수준 동시성 보장** | "다중노드 전환 결정"을 기다릴 필요가 없었다 — 낙관적 잠금(CAS)+유니크 인덱스는 **단일 노드에서 무해**하고 전환 시점에 그대로 유효. 메타 슬롯은 버전 일치 CAS, 감사 체인은 `(rkey, prevHash)` 유니크 인덱스(migration 0009)가 분기를 거부 |

> ⚠ **0009 배포 주의**: 감사 체인 유니크 인덱스는 **기존 분기가 있으면 마이그레이션이 의도적으로 실패**한다
> (끊긴 체인 위에 제약만 얹어 "무결"로 오인시키지 않기 위함). 배포 전 아래 읽기 전용 점검을 권장한다.
> ```sql
> SELECT rkey, count(*) FROM store_records
>  WHERE kind='audit' GROUP BY rkey, (data->>'prevHash') HAVING count(*) > 1;   -- 0행이어야 정상
> SELECT kind, rkey, count(*) FROM store_records
>  WHERE kind='meta'  GROUP BY kind, rkey HAVING count(*) > 1;                  -- 있으면 최신행만 남기고 자동 정리
> ```
> meta 중복은 마이그레이션이 **최신(seq 최대) 행만 남기고 자동 정리**한다(getOne 이 이미 그 행만 읽으므로 의미 변화 없음).

**§4 미확인 가설 7건**은 조치 전 실측 권장 — 특히 ①Prisma `contains` 의 LIKE 메타문자 이스케이프(`?q=%` 전건 매칭 가능 여부) ②`@@index` 실효성 EXPLAIN ③기재값 복호·폰트 실패 시 fail-open 여부.

## 트랙 E — 연동 팀 요청

### E1. edu — 멀티테넌트 기관별 consumer·registrar serial 발급 체계 (2026-07-29 접수) — **백로그(보류) · 착수 조건 = 실서비스 이후**

> **2026-07-29 결정**: 백로그로 내린다. **실서비스(go-live) 전환을 먼저 끝내고 그 이후에 진행**한다.
> 근거 — 격리 모델(특히 아래 3·4항)은 저장소 스키마와 registrar 구조를 바꾸는 결정인데, 1호 기관의
> 실운영 데이터·부하·운영 패턴을 보기 전에 확정하면 되돌리기 비싼 방향으로 굳을 위험이 크다.
> 아래 논점 정리는 **그대로 보존**한다(재개 시 여기서 이어서 시작).
>
> ⚠ **edu 는 회신 대기 중**이다. 착수 시점을 미루더라도 "실서비스 이후 진행 예정"이라는 답은
> 보내야 edu 가 2호 병원 온보딩 일정을 세울 수 있다 → 별도 액션(아래 "다음 액션" 참조).

- 전제: **2호 병원 온보딩**. edu 측 표현으로 "협의 필요"이며, 아직 요구사항이 아니라 **논의 시작점**이다.
- 성격: 단순 연동 요청이 아니라 **SaaS 멀티테넌시 축의 첫 실수요**다. 지금은 기관 구분 없이
  소비자 키(`ConsumerApp`) 단위로만 격리하고, registrar 인증서도 기관 축이 없다.
- 최소 논의 항목(설계 착수 전 확정 필요):
  1. **기관 식별자** — 어디서 오는가(sign 발급 vs 상위 시스템 부여), 소비자 키와의 관계(1:N?)
  2. **시리얼 체계** — 기관별 접두 분리 여부. 현재 `serialSeq` 는 전역 단조(v1.10.2) → 기관별로 나눌지, 전역 유지하고 주체 DN 에만 기관을 담을지
  3. **registrar 격리 범위** — 기관마다 별도 registrar 인증서인가, 공용 registrar + 기관 속성인가
     (※ edu P0 의 실원인이 **공유 registrar 폐기 연쇄**였다 — 격리 설계가 그 재발 방지와 직결된다)
  4. **데이터 격리** — 조회·목록·감사 스트림에 기관 경계를 넣을지(넣는다면 저장소 스키마 변경)
- sign 측 선행: 위 4항 중 3·4 는 SaaS 멀티테넌시 설계 없이 답할 수 없다 → 재개 시 **설계 문서부터**.
- 상태: **백로그 보류**. 다음 액션 = ①edu 에 "실서비스 이후 진행" 회신(일정 근거 제공) ②go-live 완료 후 재평가 → 설계서 작성 → 1~4항 합의.
