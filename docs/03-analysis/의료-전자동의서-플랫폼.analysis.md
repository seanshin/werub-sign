# Gap Analysis — 의료-전자동의서-플랫폼 (sign)

> **Date**: 2026-06-12
> **대상**: 설계(Plan FR-01~23 / design v0.5 / schema / conventions) vs 구현(src/, prisma/)
> **구현 단계**: Increment 1~3 (PKI 코어 + HTTP API + 폐기/SSO/Webhook). **백엔드 PoC, 영속화 in-memory**

---

## 종합 Match Rate: **약 60%** (전체 시스템 설계 대비)

> 해석: **트러스트 코어(가장 리스크 큰 부분)는 높은 충족도**, 채널/프론트엔드/영속화 계층은 미착수. 갭의 대부분은 "잘못 구현"이 아니라 **"아직 미구현(범위 잔여)"** 이다.

| 영역 | 충족도 |
|---|---|
| PKI·서명·검증·폐기 코어 | ~90% ✅ |
| 서명요청·다채널·SSO·Webhook | ~75% ✅ |
| 채널/UI(앱·태블릿·발송) | ~5% ⬜ (백엔드 외 미착수) |
| 영속화(Prisma) | 0% ⬜ (in-memory PoC) |
| 장기검증(PAdES-LTA) | 0% ⬜ |
| 컨벤션 준수 | ~80% ⚠️ |

## 갭 분류

### A. 운영 전 필수 갭 (구현 품질·정합)
1. **Prisma 영속화 어댑터** — InMemoryStore를 Repository 포트로 추상화 후 Prisma 구현 (재기동 데이터 보존)
2. **cert 발급/폐기 감사기록** — enroll/revoke에 `CERT_ISSUED`/`CERT_REVOKED` AuditTrail (conventions §4)
3. **에러 응답 포맷 통일** — 전역 ExceptionFilter로 `{error:{code,message,requestId}}`
4. **Repository 포트화** — application의 구체 store 의존 제거(클린 아키텍처 §2)
5. **RFC3161/PAdES 표준화** — 간이 TSA/서명을 표준 포맷으로(법적 증거력) — FR-03/20

### B. 계획된 점진 갭 (범위 잔여, 정상)
- 환자앱·생체/passkey·step-up(FR-14), 대면 fallback(FR-15), 발송(FR-10)
- 멀티테넌트 API 인증(FR-11), 본인인증 실연동(FR-09)
- 감사 TSA 앵커링·검증 API(FR-21), 1회용 토큰(FR-07), Webhook 재시도 배치(FR-08)
- 두 DB reconcile 배치(Plan Risk)

## 판정

- **Match Rate 59% (<90%)** — 단, 갭의 대부분은 **결함이 아니라 미착수 범위**(프론트엔드·발송·영속화·표준포맷).
- **트러스트 코어(PKI·서명·검증·폐기·SSO)는 설계와 정합하며 e2e 검증 완료** — 가장 어려운 부분이 견고.
- **다음 권장**: `/pdca iterate`로 **A(운영 전 필수 갭) 5건**을 우선 보강하면 백엔드 정합도가 크게 오른다. B(범위 잔여)는 별도 Increment로 진행.
