## 1. Overview

### 1.1 Design Goals

1. **법적 효력**: 실제 PKI 서명(`crypto.sign/verify`) + RFC3161 신뢰 시점 + 무결성 감사추적
2. **관심사 분리**: sign은 서명/무결성만, Hospital RUN은 동의서 콘텐츠/UI/업무흐름
3. **교체 가능성**: 키스토어(SOFT↔HSM), TSA(자체↔공인)를 인터페이스 뒤로 추상화
4. **clean replacement**: 기존 mock `blockchain-cert`/`document-sign` 전면 제거(개발중, 마이그레이션 없음)
5. **EMR 인증 대응**: 기능성·상호운용성·보안성 3영역 충족

### 1.2 Design Principles

- 개인키는 절대 평문/메모리 노출 최소화 → `KeySigner` 추상화 뒤에서만 서명
- 모든 상태변화는 `AuditTrail`(append-only 해시체인)에 기록
- Hospital RUN ↔ sign 통신은 멱등(idempotencyKey) + Webhook HMAC
- 민감정보·키·서명원본은 원내망 고정, DMZ엔 서명 웹뷰만 노출

## 2. Architecture

> **관계 정의(필독)**: sign↔Hospital RUN의 관계·책임경계·연동 인터페이스는 [integration-hospitalrun.md](../integration-hospitalrun.md)에 통합 정의됨.
> 요약: **Provider(sign, 전자서명 트러스트) · Consumer(Hospital RUN, 업무 시스템)** — 독립 배포·독립 DB, 계약(REST/Webhook/SSO)으로만 결합. 키·서명·증거는 sign, 동의서·환자·UI·채널은 Hospital RUN 소유. §2.5~2.7·§19는 이 관계의 채널·신뢰경계 상세.

### 2.1 Component Diagram

```
                         [인터넷]  환자/보호자 스마트폰(포털 앱)
                              │ HTTPS (환자앱 API primary + 서명 웹뷰 fallback)
 ┌──────────────── DMZ ───────┴───────────────────────────┐
 │  sign-gateway (Reverse Proxy)                           │
 │   ├─ 환자포털 앱 API 프록시(primary) + 서명 웹뷰(fallback)│
 │   ├─ IdentityProvider 중계 (휴대폰명의/PASS/카카오)     │
 │   └─ Notifier (카카오 알림톡 / SMS)                     │
 └──────────────────────────┬─────────────────────────────┘
                            │ 제한 포트 / mTLS
 ┌──────────── 원내망 (On-Premise) ──┴─────────────────────┐
 │  Hospital RUN (HIS, NestJS)                             │
 │   consent / consent-template / portal / workstation     │
 │        │  POST /v1/requests           ▲ Webhook         │
 │        ▼                              │                 │
 │  sign-core (NestJS, 별도 DB)                            │
 │   ┌──────────────┬──────────────┬───────────────────┐  │
 │   │ Signing      │ PKI/CA       │ Timestamp(TSA)    │  │
 │   │ Verification │ KeySigner    │ AuditTrail        │  │
 │   │ Request/Flow │ (SOFT→HSM)   │ AuditCertificate  │  │
 │   └──────────────┴──────────────┴───────────────────┘  │
 │   sign-db (PostgreSQL): cert/key/sig/ts/audit          │
 │   DocumentStore: 원본·서명본(PDF) 보관                 │
 └─────────────────────────────────────────────────────────┘
```

### 2.2 Data Flow (원내 대면 서명)

```
1. 의료진: Hospital RUN에서 동의서 생성(ConsentForm)
2. Hospital RUN → sign: POST /v1/requests {externalDocId, documentHash, participants[]}
3. sign: SignatureRequest 생성(CREATED) → 1회용 token 발급 → AuditTrail(CREATED)
4. 태블릿: 서명 웹뷰 open(token) → AuditTrail(VIEWED)
5. 본인확인(대면=INPERSON) → AuditTrail(IDENTITY_VERIFIED)
6. 서명: 손글씨 캡처 + KeySigner.sign(documentHash) → Signature(실 서명값)
7. TSA: Timestamp 발급(RFC3161) → Signature.timestampId
8. 다자 순차 반복(환자→보호자→의사→…) → 모두 SIGNED
9. sign: status=COMPLETED → AuditCertificate 생성 → AuditTrail(COMPLETED)
10. sign → Hospital RUN: Webhook request.completed → ConsentForm.status=SIGNED + 참조 저장
```

### 2.3 Data Flow (원외 비대면 서명)

```
2'. Hospital RUN → sign: POST /v1/requests {signMode:REMOTE, channel:KAKAO, 연락처}
3'. sign(DMZ Notifier): 카카오 알림톡/SMS로 서명 링크(token) 발송 → AuditTrail(SENT)
5'. 본인확인(MOBILE_NAME/PASS): IdentityProvider 중계 → IdentityVerification(SUCCESS)
    └ 실패 시 서명 차단(상태 IDENTIFIED 미진입)
6'~10' : 대면과 동일 (서명→TSA→감사추적→Webhook)
```

### 2.5 환자·보호자 채널 — 개인인증 모델 (기획 조정 v0.3)

서명 채널을 **개인인증된 환자포털 앱 하나로 통합**(원내·원외 동일), **대면 태블릿은 fallback**으로 유지.

```
[등록 1회]  앱 설치 → 휴대폰 본인인증(PASS/명의) → CI 확보
            → IdentityVerification(method=PASS|MOBILE_NAME, ciHash) 저장
            → 환자 Certificate 발급 (CI 귀속 = "본인 서명" 법적 근거)  ※ validator 격차 해소
[로그인]    앱 생체/passkey/PIN (간편 재인증)
[서명]      저위험: 앱 로그인 상태로 서명
            고위험(SURGERY/ANESTHESIA/DNR): step-up 재인증(생체/PASS)  ← §15 매트릭스
[채널]      원내 환자 = 자기 폰 앱(또는 원내 공용기기 앱 로그인)
            원외 환자 = 동일 앱(집)
            → 앱 → DMZ(포털 API) → sign-core(원내): PKI 서명+TSA+감사추적
            → 키·서명원본·민감정보 원내 고정 (외부 HSM 불필요)
[Fallback]  앱 미설치/고령/외국인/응급/보호자 = 원내 대면 태블릿(ConsentSigningDevice) 유지
```

| 항목 | 설계 |
|---|---|
| 개인인증(enrollment) | **휴대폰 본인인증(PASS/명의) + CI 확보** → `IdentityVerification` + 환자 `Certificate` 발급 근거 |
| 재인증(login) | 앱 생체/passkey(WebAuthn)/PIN — 기존 Hospital RUN passkey 자산 재활용 |
| step-up(서명) | 고위험 동의서는 서명 직전 재인증, `Signature.identityVerificationId`에 해당 인증 연결 |
| 채널 통합 | 원내/원외 동일 앱 흐름 → 카카오 토큰 웹뷰는 앱 미설치자용 보조로 축소 |
| fallback | 대면 태블릿 유지(앱 우선·대면 보조 하이브리드) |
| 자산 | 기존 Expo 환자앱·포털·passkey 확장 |

> 효과: (1) 기존 MRN+생년월일 약한 인증 → 강한 본인확인 대체, (2) **환자 인증서 발급 근거 확립**(validator §2 격차 해소), (3) 채널 단순화, (4) **AWS HSM 불필요**(키 원내 고정 유지) → 원내 물리 HSM이면 충분.

### 2.6 의료진(STAFF) 채널 — 의료진 포털

동의서는 환자 외 **의사 서명·간호사 확인·입회인**이 함께 들어감. 의료진은 환자와 **다른 인증 모델**(이미 강한 내부 인증 보유).

```
[의료진 포털 (PC/앱) — 기존 Hospital RUN HIS 인증 재활용]
  로그인:  HIS 계정(JWT+RBAC) + passkey/SSO + (민감조작) step-up
  인증서:  직원 온보딩 시 면허확인(licenseNumber/licenseType) + 직원ID 바인딩
           → STAFF Certificate 발급 (ownerType=STAFF)
  서명:    의료진 포털에서 의사 서명 / 간호사 사전확인 / 입회 서명 (signMode=PC)
  요청생성: 의사가 동의서 생성 → sign-core에 환자 서명요청 발행 + 워크스테이션 큐(SSE)
```

| 항목 | 환자/보호자 (§2.5) | 의료진 (§2.6) |
|---|---|---|
| 채널 | 환자포털 앱(원내/원외) + 대면 fallback | 의료진 포털(PC/앱) |
| 등록 본인확인 | 휴대폰 본인인증(PASS/명의)+CI | HIS 계정 + 면허확인(licenseNumber) |
| 재인증 | 생체/passkey, 고위험 step-up | passkey/SSO, 민감조작 step-up |
| Certificate 귀속 | `ownerType=PATIENT`, `ciHash` | `ownerType=STAFF`, `licenseNumber`+직원ID |
| IdentityVerification.method | PASS / MOBILE_NAME | STAFF_SSO (내부 인증) |

### 2.7 통합 서명자 매트릭스

| signerRole | 채널 | 인증서 귀속 | 비고 |
|---|---|---|---|
| PATIENT | 환자앱(원내/원외) / 대면 fallback | CI(ciHash) | 본인 |
| GUARDIAN | 환자앱(보호자 본인) / 대면 | CI + 관계·법적근거 | 미성년·의식불명 등 |
| DOCTOR | 의료진 포털 | 면허번호+직원ID | 설명·서명 주체 |
| NURSE | 의료진 포털 | 직원ID(+면허) | 사전확인(nurseCheck) |
| WITNESS(직원) | 의료진 포털 / 대면 | 직원ID | 입회 |
| WITNESS(외부) | 대면 | 임시·제한 인증서 | 외부 입회인 |

> 한 `SignatureRequest`에 환자(앱)·의사(포털)가 **서로 다른 채널에서 순차 서명**해도 동일 봉투·동일 무결성(PKI+TSA+감사추적)으로 묶임. `SignerParticipant.signerType`(PATIENT/STAFF/GUARDIAN)으로 채널·인증모델 분기.

## 3. Data Model

전체 엔티티는 [Phase 1 Schema](../../01-plan/schema.md) 참조. 핵심 관계:

```
SignatureRequest 1──N SignerParticipant 1──1 Signature N──1 Certificate 1──1 KeyMaterial
        │                                      │
        ├──N AuditTrail (해시체인)             ├──1 Timestamp (TSA)
        └──1 AuditCertificate                 └──1 IdentityVerification
```

매핑: `SignatureRequest.externalDocId = ConsentForm.id` (externalDocType=CONSENT).

### 3.1 Hospital RUN 측 변경 (clean replacement)

| 대상 | 조치 |
|---|---|
| `BlockchainCertificate`, `DocumentSignature`, `SignedDocument` (mock) | **제거** 또는 sign 참조로 대체 |
| `blockchain-cert`, `document-sign` 모듈 | **제거** (sign-core가 대체) |
| `ConsentForm.blockchainSignature`(mock) | 제거 |
| `ConsentForm` 신규 필드 | `signatureRequestId`(uuid), `signStatus`(sign 동기화), `auditCertUri` 추가 |
| `consent`/`portal` 서명 호출부 | sign-core API 호출 + Webhook 수신으로 교체 |

> 손글씨 서명 이미지(`patientSignature` 등)는 표시용으로 유지 가능하나, **법적 효력의 근거는 sign의 PKI 서명**으로 일원화.

## 4. API Specification

### 4.1 sign-core REST (원내, Hospital RUN ↔ sign)

| Method | Path | Description | Auth |
|--------|------|-------------|------|
| POST | /v1/requests | 서명요청 생성 | API Key (mTLS) |
| GET | /v1/requests/:id | 요청 상태 조회 | API Key |
| POST | /v1/requests/:id/cancel | 요청 취소/철회 | API Key |
| GET | /v1/sign/:token | 서명 웹뷰 데이터 로드 | 토큰 |
| POST | /v1/sign/:token/identify | 본인확인 수행 | 토큰 |
| POST | /v1/sign/:token/submit | 서명 제출 | 토큰 |
| GET | /v1/verify/:requestId | 서명/문서 무결성 검증 | API Key |
| GET | /v1/requests/:id/audit-certificate | 감사추적인증서(PDF) | API Key |

### 4.2 Detailed Spec

#### `POST /v1/requests` — 서명요청 생성

**Request:**
```json
{
  "idempotencyKey": "consent-<uuid>-v1",
  "externalSystem": "HOSPITALRUN",
  "externalDocType": "CONSENT",
  "externalDocId": "<ConsentForm.id>",
  "patientRef": "<patientId>",
  "title": "수술 동의서",
  "documentHash": "<sha256 of sealed content>",
  "documentVersion": 1,
  "signMode": "TABLET",            // TABLET | PC | PORTAL | REMOTE
  "channel": "INPERSON",           // INPERSON | KAKAO | SMS
  "callbackUrl": "https://his.internal/api/v1/consent/webhook",
  "expiresInSec": 86400,
  "participants": [
    { "signerRole": "PATIENT", "signerType": "PATIENT", "externalSignerRef": "<patientId>",
      "displayName": "김환자", "signOrder": 1, "requiredIdentityLevel": "INPERSON" },
    { "signerRole": "DOCTOR", "signerType": "STAFF", "externalSignerRef": "<userId>",
      "displayName": "이의사", "signOrder": 2, "requiredIdentityLevel": "STAFF_SSO" }
  ]
}
```

**Response (201):**
```json
{
  "requestId": "<uuid>",
  "status": "CREATED",
  "tokens": [
    { "participantId": "<uuid>", "signerRole": "PATIENT", "token": "<64hex>", "signUrl": "https://sign.dmz/v1/sign/<token>" }
  ],
  "expiresAt": "2026-06-13T05:00:00Z"
}
```

**Errors:** `400` 검증 실패 · `409` idempotencyKey 중복(기존 응답 반환) · `401` 인증 실패

#### `POST /v1/sign/:token/submit` — 서명 제출

**Request:**
```json
{
  "handwrittenImage": "data:image/png;base64,...",   // 표시용(선택)
  "guardian": { "name": "박보호", "relation": "SPOUSE", "legalBasis": "FAMILY" }  // GUARDIAN 시
}
```
> 서명 대상 해시는 서버가 `documentHash`로 고정(클라이언트 입력 신뢰 안 함). 서버에서 `KeySigner.sign()` 수행.

**Response (200):**
```json
{
  "signatureId": "<uuid>",
  "signedAt": "2026-06-12T05:01:00Z",
  "timestamp": { "genTime": "2026-06-12T05:01:00Z", "tsaProvider": "SELF" },
  "requestStatus": "IN_PROGRESS"   // or COMPLETED
}
```
**Errors:** `403` 본인확인 미완(IDENTIFIED 아님) · `409` 이미 서명됨 · `410` 토큰 만료

#### `GET /v1/verify/:requestId` — 무결성 검증

**Response (200):**
```json
{
  "requestId": "<uuid>",
  "documentIntegrity": "VALID",          // 원본 해시 대조
  "signatures": [
    { "signerRole": "PATIENT", "certSerial": "CERT-...", "cryptoVerify": "VALID",
      "timestampValid": true, "certValidAtSign": true, "identityMethod": "INPERSON" }
  ],
  "overall": "VALID"
}
```

### 4.3 Webhook (sign → Hospital RUN)

`POST {callbackUrl}` — 헤더 `X-Sign-Signature: <HMAC-SHA256(payload, secret)>`

```json
{
  "eventType": "request.completed",      // request.completed | request.failed | request.revoked | signer.signed
  "eventId": "<uuid>",                    // 멱등 처리용
  "requestId": "<uuid>",
  "externalDocId": "<ConsentForm.id>",
  "status": "COMPLETED",
  "verifiedHash": "<sha256>",
  "auditCertUri": "/v1/requests/<id>/audit-certificate",
  "occurredAt": "2026-06-12T05:02:00Z"
}
```
- 재시도: 지수백오프 Outbox(`WebhookDelivery`), Hospital RUN은 `eventId`로 멱등 처리
- 수신 시 Hospital RUN: `ConsentForm.status=SIGNED`, `signatureRequestId`/`auditCertUri` 저장

## 5. Key Sequences

### 5.1 PKI 서명 (서버 측, SOFT 모드)

```
submit(token)
 └ 본인확인 상태 검증 (participant.status == IDENTIFIED)
 └ KeySigner.sign(documentHash, signerCert.keyId):
      SOFT: KMS로 keyRef 복호화 → 메모리 키로 crypto.sign(SHA256) → 키 즉시 폐기
      HSM : PKCS#11 C_Sign(keyHandle, documentHash)   ← 추후 동일 인터페이스
 └ Timestamp: TSA.stamp(sha256(signatureValue)) → TimeStampToken
 └ Signature 저장(value, algo, timestampId, identityVerificationId, ip/ua/device)
 └ AuditTrail.append(SIGNED, prevHash→entryHash)
 └ completedSigners++ ; 모두 완료 시 COMPLETED → AuditCertificate + Webhook
```

### 5.2 검증 (verify)

```
for each signature:
  cryptoVerify    = crypto.verify(SHA256, signedAttrs, cert.publicKey, signatureValue)  // §10 PAdES
  certValidAtSign = (cert.notBefore ≤ ts.genTime ≤ cert.notAfter)                       // ★ TSA 시각 기준
  notRevokedAtSign= revocationStatusAt(cert, ts.genTime) == GOOD                        // §11 CRL/OCSP
  notSuspended    = cert.status ≠ SUSPENDED@signTime
  timestampValid  = TSA.verify(tsToken, sha256(signatureValue))
  chainValid      = verifyChain(cert → issuerCA → rootCA)                                // §13 CA
overall = documentHash 일치 && 모든 signature(cryptoVerify & certValidAtSign &
          notRevokedAtSign & notSuspended & timestampValid & chainValid)
```
→ mock과의 결정적 차이: **공개키로 실제 서명을 검증**(기존은 sha256 단순 해시).
→ **서명시점 유효성은 TSA `genTime` 기준**(서버시계 불신). 만료 후 검증은 §10 LTV로 보장.

|---|---|

## 10. [Critical] 서명 포맷 & 장기검증(LTV)

**결정: PAdES (PDF Advanced Electronic Signatures)** 채택. 동의서가 PDF이므로 자연스럽고, 한국 의료/공공에서 보편적.

| 항목 | 결정 |
|---|---|
| 서명 대상 | PDF에 봉인된 **signed attributes(CAdES 호환)** — `Signature.signedAttrsHash`가 서명 대상. `documentHash`는 그 signedAttrs에 포함되는 messageDigest. → **스키마-설계 모순 해소** |
| 레벨 | **PAdES-B-LT** 기본, 완료 시 **PAdES-B-LTA**(아카이브 타임스탬프)로 승격 |
| LTV 구성 | 서명에 **인증서 체인 + CRL/OCSP 응답 + TSA 토큰**을 DSS(Document Security Store)에 봉인 |
| 보존 | 의료법상 동의서 보존기간(수술 동의서 등 장기) 동안 **인증서 만료 후에도 검증 가능** |
| 갱신 | 아카이브 TS 만료 전 재타임스탬프(LTA 갱신) 배치 |

→ `Signature`에 `format`("PAdES-B-LTA"), `dssData`(Json: chain/crl/ocsp/ts) 필드 추가. 서명본 PDF는 `documentUri`(DocumentStore) 보관.

**근거**: verify가 `certValidAtSign`만 보면 만료 후 증거능력 약화. LTV 봉인으로 "서명 당시 유효+미폐기"를 서명 자체에 고정.

## 11. [Critical] 인증서 폐기 검증 (CRL/OCSP)

기존 설계는 자기 DB `Certificate.status`만 조회 → 표준 폐기검증 아님. 보강:

```prisma
model CertRevocation {           // CRL 엔트리
  id           String @id @default(uuid()) @db.Uuid
  certId       String @db.Uuid
  serialNumber String @db.VarChar(64)
  revokedAt    DateTime @db.Timestamptz()
  reason       String @db.VarChar(50)   // keyCompromise, superseded, cessationOfOperation, ...
  crlNumber    Int                       // CRL 버전
}
```

| 기능 | 설계 |
|---|---|
| OCSP 응답자 | `GET /v1/ocsp/:serial` → GOOD/REVOKED/UNKNOWN (RFC6960 호환 응답) |
| CRL 발행 | `GET /v1/crl` → 주기 발행(서명된 CRL), `crlNumber` 증가 |
| 폐기 시점검증 | verify는 **서명 시각(TSA genTime) 기준** 폐기여부 판단(`revocationStatusAt`) |
| 외부 검증 | FR-11 외부 시스템도 OCSP/CRL로 sign 인증서 검증 가능 |
| LTV 연계 | 서명 시점 OCSP/CRL 응답을 §10 DSS에 봉인 |

## 12. [Critical] 원외 토큰 보안 모델

## 13. [Critical] CA 루트키 보호 (2단 CA)

CA 개인키 = 전체 신뢰의 단일 위탁점 → 일반 서명키와 분리:

```
[Root CA]  오프라인 보관(에어갭/HSM), 평시 미사용, 중간 CA 발급에만 사용
   │
[Issuing CA(중간)]  온라인, 환자/직원 인증서 발급. 폐기 가능
   │
[End-entity certs]  환자·보호자·의료진
```

| 항목 | 설계 |
|---|---|
| Root 키 | 오프라인(에어갭) 또는 HSM 최상위, `KeyMaterial.ownerType=CA` 별도 보호등급 |
| Issuing CA | 온라인, 침해 시 Root가 폐기·교체 |
| 부트스트랩 | 초기 1회 Root 생성·중간 CA 발급 절차 문서화(수동 의식) |
| SOFT 단계 | Root도 SOFT면 위험 → **Root만 우선 HSM/에어갭** 권고(키스토어 추상화로 분리 가능) |

## 14. [High] 상태머신 엣지케이스

| 케이스 | 처리 |
|---|---|
| 동시 서명 | `SignerParticipant` 행 락(SELECT FOR UPDATE) + `completedSigners` 원자 증가. 순서 위반 submit은 409 |
| 부분서명 중 철회 | 이미 생성된 Signature/Timestamp는 **보존(무효화 아님)**, Request만 `REVOKED`. 감사상 "철회 전 N명 서명" 기록 유지 |
| 만료 전이 | 스케줄러가 `expiresAt` 경과분 `IN_PROGRESS→EXPIRED` 전이 + 경합 방지(만료 후 submit은 410) |
| DECLINED | 필수 서명자 1명이라도 거부 → Request `FAILED`(설정상 부분완료 허용 시 정책 분기) |

| 재서명(FR-13) | 만료/거부/문서변경 시 **신규 SignatureRequest** 발급(기존 봉투 불변), Hospital RUN이 재요청 |

## 19. v0.4 채널 검증 보강 (재검증 78점 대응)

### 19.1 [Critical C-1] 인증서 발급 시퀀스 & API

**환자 인증서 발급 (§5.3)** — 앱 등록 시 1회:
```
앱 등록 → 휴대폰 본인인증(PASS/명의) → CI 확보
 └ IdentityVerification(method=PASS|MOBILE_NAME, ciHash, result=SUCCESS)
 └ 키쌍 생성 KeySigner.generate(ownerType=PATIENT) → KeyMaterial(공개키, keyRef)
 └ Issuing CA가 CSR 서명 → Certificate(ownerType=PATIENT, ciHash 귀속, notAfter=유한, identityVerificationId)
 └ AuditTrail.append(CERT_ISSUED)
```
**STAFF 인증서 발급 (§5.4)** — 직원 온보딩 시:
```
HIS 온보딩 → 면허확인(licenseNumber/Type) + 직원ID
 └ IdentityVerification(method=STAFF_SSO)
 └ 키쌍 생성 → Issuing CA 서명 → Certificate(ownerType=STAFF, licenseNumber+직원ID 귀속)
 └ AuditTrail.append(CERT_ISSUED)
```
| API | 설명 |
|---|---|
| `POST /v1/certificates/enroll` | { ownerType, identityProof(PASS/SSO), csr? } → Certificate. 환자=앱, STAFF=온보딩 |
| `POST /v1/certificates/:serial/revoke` | status=REVOKED + CertRevocation + AuditTrail(CERT_REVOKED) |

→ AuditTrail 필수 이벤트에 **CERT_ISSUED / CERT_REVOKED** 추가(conventions §4·schema 동기화).

### 19.2 [Critical C-2] STAFF 인증 신뢰경계 & 진입 API

sign(독립서비스)이 Hospital RUN 인증을 신뢰하는 경계 정의:
- HIS가 발급한 **SSO 토큰(OIDC/JWT)** 을 sign이 **JWKS 공개키로 검증**(또는 introspection). 신뢰 발급자 = HIS.
- step-up 결과는 토큰 클레임(`acr`/`amr`)으로 전달 → sign이 `IdentityVerification(method=STAFF_SSO, providerTxId=jti)` 기록.
- **STAFF 서명 진입 API**: `POST /v1/sign/staff` (Authorization: Bearer \<HIS SSO 토큰\>) — 환자 1회용 토큰(§12)과 **분리**. 원내 PC→sign-core 직접(mTLS), DMZ 불요.
- 환자 토큰 모델(§12 phoneHash 바인딩)은 STAFF에 미적용.

### 19.3 [High H-1] 데이터플로우 정본 일원화

- **정본**: 환자 = 앱 채널 primary(§2.5), 의료진 = 포털(§2.6).
- §2.2(태블릿 대면)·§2.3(카카오 웹뷰)은 **fallback 경로로 재정의** — 앱 미설치/응급/보호자/외부입회인용.
- 앱 채널 단계: 앱(로그인) → DMZ 포털 API → sign-core(서명요청/서명) → PKI+TSA+감사 → Webhook.

### 19.4 [High H-2] 채널 ↔ signMode ↔ 인증레벨 매트릭스

| 채널 | signMode | 기본 requiredIdentityLevel |
|---|---|---|
| 환자포털 앱(원내/원외) | **APP** | 등록 PASS/명의, 고위험 **APP_STEPUP** |
| 대면 태블릿(fallback) | TABLET | INPERSON |
| 카카오 웹뷰(fallback) | REMOTE | MOBILE_NAME / PASS |
| 의료진 포털 | PC | **STAFF_SSO** (+민감 step-up) |

→ schema `signMode`에 **APP**, `requiredIdentityLevel`에 **APP_STEPUP / STAFF_SSO** 추가.

### 19.5 [High H-3] 외부 입회인 임시 인증서

- `SignerParticipant.signerType`에 **WITNESS_EXTERNAL**, `Certificate.ownerType`에 **WITNESS** 추가 (KeyMaterial과 enum 통일: CA/STAFF/PATIENT/WITNESS/SERVICE).
- 임시·제한: 단기 `notAfter`(예 24h), 1회성, keyUsage 서명한정. 대면 신원확인 기록(`IdentityVerification method=INPERSON`).

### 19.6 [High H-4] 다채널 순차 서명 상태머신

- `signOrder`는 **채널 무관 전역 게이팅**: 앞 순번 미서명 시 뒤 순번(채널 불문) submit → 409.
- 채널별 세션·만료 **분리**: 환자 앱 세션(§12 SignSession) vs STAFF 포털 세션(SSO 토큰 TTL) 독립.
- 부분완료 알림: 환자=앱 push(FCM), 의료진=워크스테이션 SSE(기존 Hospital RUN 자산).
- 동시 submit: §14 행 락 유지(채널 교차에도 동일 SignatureRequest 단일 락).

### 19.7 [Medium] 기타 정합

- DOCTOR 예시 `requiredIdentityLevel` NONE→STAFF_SSO(반영), §15에 STAFF 인증레벨 행 포함.
- 헤더 Version 0.4(반영). KeyMaterial/Certificate `ownerType` enum 통일.
- FR 추적: §2.5=FR-14/15, §2.6/2.7=FR-16/17, §19.1=FR-14·16, §19.6=FR-17.
